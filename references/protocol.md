# Review protocol

All IDs are opaque strings generated by the runner or host. All schemas are English and versioned.

## Run manifest

A run records `schema_version`, `run_id`, `created_at`, `workspace`, `context_digest`, `target_digest`, `stage`, `intensity`, `domains`, `confirmed`, and `tasks`. The confirmed plan is also saved as `plan.json`. Each task declares `task_id`, `reviewer_id`, `kind` (`cli` or `native_subagent`), `domain`, `language`, `methods`, `assignment`, and optional `time_budget_seconds` and `token_budget`. See `templates/plan.example.json`. Confirmation is a host-recorded user decision, not a security boundary enforced against a dishonest caller.

## Git checkout provenance

Git-isolated plans declare `isolation: "git-worktree"`, `head_ref`, and `base_ref`. The manifest records resolved commit provenance and each task's absolute workspace and retained/removed lifecycle state. All tasks start detached at the same pinned head. The original `workspace` remains the source repository; the runner's `{workspace}` placeholder and process cwd refer to the task checkout. Task workspaces are siblings of the task evidence hierarchy, not valid evidence references themselves. Native assignments carry the same cwd and provenance. Checkout metadata survives imports and collection; removal changes lifecycle metadata without deleting evidence. See `worktrees.md` for explicit main-Agent cleanup and follow-up policy.

## Task execution

Each task directory contains `assignment.md`, `execution.json`, `result.json` when submitted, `stdout.log` and `stderr.log` for CLI runs, and `evidence/`. Execution metadata records status, available timing and exit information, configured/runtime model uncertainty, and budget enforcement. Task identity, language, and methods are registered in the manifest. Execution status is separate from review status: `pending`, `running`, `succeeded`, `failed`, `timed_out`, `cancelled`, or `blocked`. Native submissions record host-reported completion rather than inventing CLI usage or timing.

Execution metadata records whether a submission was accepted and its result-file SHA-256. Coverage requires both execution success and a fresh accepted, currently valid complete submission. Parse/materialization failures do not accept pre-existing files; later result-file changes invalidate the recorded digest. Historical runs without acceptance metadata remain archived but do not automatically count as coverage. Native import attempts retain uniquely named source/execution records under `import-attempts/`; corrected failed imports can be retried without discarding earlier artifacts.

## Reviewer result

A valid result contains `schema_version`, `task_id`, `reviewer_id`, `domain`, `target_digest`, `review_status` (`complete`, `partial`, or `blocked`), `scope_checked`, `methods_used`, `checks_performed`, `findings`, `assumptions`, `limitations`, and `evidence`. Each finding contains `id`, `severity`, `confidence`, `title`, `location`, `failure_scenario`, `evidence`, `impact`, and `recommendation`. Severity is `blocker`, `high`, `medium`, `low`, or `note`; confidence is `high`, `medium`, or `low`.

Malformed output is a validation failure, never an empty finding list. Evidence references must name existing task-relative files under `evidence/`; external URLs or command output should be recorded in an evidence file with source and timestamp. Validation checks structure and references, not semantic truth.

## JSON transport and failure classification

The reviewer contract requires one JSON object, without Markdown fences or surrounding prose. This requirement is enforced by strict parsing and field validation after execution; a prompt asking for JSON is not model-side constrained generation. CLI JSON/event flags may wrap the answer in an envelope or NDJSON stream, and do not necessarily constrain the review content. Use verified adapter decoding; do not blindly add a CLI's `--json` flag or heuristically extract a plausible object from arbitrary logs. Where a CLI supports output schemas, a verified schema can improve reliability, but local validation is still required.

Keep execution failures, JSON syntax/transport failures, schema/identity failures, evidence-reference failures and incomplete review status distinct. A valid JSON object may still fail evidence checks. A failed parse must never reuse a stale result or count as a completed domain. Preserve raw output and explain the concrete failure before arranging a bounded retry or host-assisted import. Human-facing summaries remain natural language; JSON is the inter-agent transport, not the final user experience.

## Read-only evidence transport

A reviewer that cannot write files may add an optional `inline_evidence` object mapping safe basenames to non-empty text, and reference each as `evidence/<basename>` in its findings and top-level evidence array. For example:

```json
{
  "inline_evidence": {"source-trace.txt": "Reviewer-authored source trace, commands, results and limitations."},
  "evidence": ["evidence/source-trace.txt"]
}
```

The runner materializes these text artifacts during successful execution or explicit import, applies best-effort redaction, and keeps the original submission/output separately. Basenames cannot include directories, absolute paths or traversal. Existing evidence must never be overwritten. Evidence transported this way is reviewer-authored, not an independent execution attestation. Mark unavailable tests as unperformed; do not invent logs or screenshots. Existing file references remain mandatory in the normalized result.

## Synthesis

The main Agent adds verification decisions without overwriting original results. Each finding is `accepted`, `rejected`, or `needs_verification`, with rationale and links to source tasks/evidence. Deduplicate only when domain, location, claim, and failure scenario substantially overlap; preserve distinct evidence and disagreements. Report missing domains and failed tasks.
